One contract, two backends

How the Maktub prototype is put together: a single-file web client whose UI only ever speaks the API contract, an in-page mock backend for standalone use, and a reference Go backend serving the same contract over real HTTP and WebSocket. The client picks between them at boot.

As of 2026-09-19 · branch claude/dating-app-bvd8yy · contract docs/spec/02-api-contract.md

System diagram

Everything the UI does goes through apiCall() and the frame handlers; the transport switch is the only place that knows whether the other side is in-page JavaScript or a Go process.

Why two backends?

The published prototype runs in a sandbox that blocks network calls, so it carries its own backend. The Go server exists so the same client can be exercised against a real process — swapping in production infrastructure is a transport change, not a rewrite.

Parity is tested, not assumed

test-api.js checks the contract against the mock; test-server.js boots the Go binary and re-checks it over real HTTP, then drives the served client through signup → match → chat on a live WebSocket.

Where production plugs in

The Go store is a mutex-guarded in-memory struct behind serializers. Postgres (records), Redis (presence/throttles), and S3/CDN (photos) replace it behind the same route handlers.

Message round trip

The one flow that exercises most of the machine — identical over the mock's simulated frames and the real WebSocket.

WebSocket frames

Frame shape { type, data, client_id? } over /v1/ws?token=…. The mock delivers the same frames in-page; the Go server delivers them over a real socket with a 30-second heartbeat.
